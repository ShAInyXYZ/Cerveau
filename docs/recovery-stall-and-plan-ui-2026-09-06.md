## Contract changes

1. Empty, length-stopped replies with no tool calls get at most two output-shape
   reissues per step attempt, using the existing lower-thinking fallback. They
   do not consume actionable iterations, but still count in model-call telemetry
   and existing token/time guards. The maximum extra allowance is two calls,
   not another general iteration-budget extension. Off-thinking truncation or
   exhaustion stops with an explicit output-limit reason. Partial tool arguments
   are not reclassified as executable repairs.
2. During recovery, four model rounds with no observed workspace change trigger
   one pinned checkpoint: use existing evidence for one small structured repair,
   or state the exact blocker. This is coaching, not a forced edit or a diagnosis
   generated by the harness. The existing fingerprint uses file metadata, not a
   semantic analysis of progress.
3. `recovery_read` reports `total_bytes` and useful offset bounds. Snapshot reads
   compare their SHA-256 against current workspace bytes at read time. Matching
   copies explicitly say they contain the same source, not a pre-failure version.
   Comparison unavailability is reported instead of implying inequality or safety.
4. `recovery_read({query:"rawBlock"})` searches literal, case-sensitive text in
   this plan's recorded tool payloads. At most 20 short results per page; `after`
   continues by event ID. Read a resulting `id` with byte `offset` for full source.
   Previous plans and recursive recovery-read output are excluded from search.
   A recorded tool call is evidence of an attempt, not proof it succeeded.
5. New assistant journal events retain the server's `finish_reason`. Output
   retries and the recovery checkpoint have explicit journal notes.
6. Report counts separate `needs_reverify`, `pending`, `running`, `unverified`
   and actual `skipped` states. Stale pass summaries say “Previously passed;
   awaiting recheck,” never unqualified current verification. Existing historical
   chat reports are not rewritten; new reports and live projections use the fix.
7. Both plan views show meaningful status/count labels. The embedded Planner
   also says “Previously passed · awaiting recheck” and labels file-presence
   counts as files, not check results. Its single-step recovery button names and
   explicitly targets the blocker before stale prerequisites. The chat action
   still repairs, rechecks, then continues the plan; the Planner single-step
   action still stops after its scoped work.

Planner assets are **1.5.1**, still embedded with built-in precedence. Installed
copies are untouched. Sampling and session thinking settings are unchanged.
Read-only recovery Bash, structured edits, verified source copies, prerequisite
rechecks, single-step/selected scope and the existing guards remain in force.
